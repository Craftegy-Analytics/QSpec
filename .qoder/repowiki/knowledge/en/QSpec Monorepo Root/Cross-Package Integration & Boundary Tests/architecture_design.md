Tests are organized by concern rather than by package: `boundaries.test.ts` scans every `packages/*` manifest and source tree to enforce browser-safety, ESM-only, sideEffects:false, MIT licensing, engine floor, export surface, and no eval/Function usage; `pipeline.test.ts` exercises the in-memory data path (memory source + transforms + charts) against `@qspecs/core`; `postgres-pipeline.test.ts` runs the same pipeline against a real PostgreSQL container via testcontainers, covering SPEC.md §116 from JSON manifest through SQL compilation, execution, normalization, transform chain, and chart presentation; `react-pipeline.test.tsx` extends that flow with an HTTP boundary (`createQSpecHandler` / `createHttpExecutor`) and a jsdom React tree (`QSpecProvider` → `QSpecResource` → `QSpecChart`), asserting that no SQL, credentials, or connection strings leak over the wire or into the DOM; `cli-bin.test.ts` spawns the compiled `packages/cli/dist/bin.js` through both direct invocation and a `node_modules/.bin`-style symlink to verify the shipped entry point actually runs; `definition-of-done.test.ts` executes the documented acceptance snippet from SPEC.md §115; `docs-drift.test.ts` and `react-http-parity.test.ts` cover documentation and parity concerns. Each suite is self-contained, uses Vitest's `describe.skip` pattern when Docker/testcontainers is unavailable, and pins timeouts at the top of each file.
